# Open tools still cannot write FO4 ragdolls

> **Corrections from this repo's own findings (2026-10-25).** (1) The AnimTextData file name is known here:
> CRC-32 of the lower-case folder list joined by `|` (high half) and of the behaviour graph path (low half),
> zero start, no final inversion; it reproduces vanilla's and DLC01's names
> ([fo4_spikes.md#spike-4-gun-clips](../fo4_spikes.md#spike-4-gun-clips)). (2) Root motion written as
> zeros affects only clips this repo writes (`write_fo4_animation`); the creature speed work reads FNV's own `.kf`
> root motion and FO4's movement types, not FO4 clips, so it is not affected
> ([fo4_pipeline.md#creature-speed](../fo4_pipeline.md#creature-speed)). Writing real root motion is
> still needed for any converted locomotion clip.
>
> **Addendum: IceStormNG's tutorial read (Nexus 56676, local copy).** The FO4 ragdoll and character controller
> live in `skeleton.nif` (Bethesda's exporter + Elric; vanilla creature skeleton NIFs hold `bhkRagdollSystem` with
> `hknpRagdollData`), and the game `skeleton.hkx` can be skeleton-only. Behaviours are authored as TagXML and packed
> with hkxpack. The tutorial also lists the engine's graph variables and events and the IDLE-record actor actions.
> So the "no open hknp ragdoll writer" gap may be closed by Elric itself: FNV skeletons carry an authored ragdoll in
> the pre-Elric terms. Details: [fo4_spikes.md#own-rigs](../fo4_spikes.md#own-rigs).

Only one team has publicly shipped working Fallout 4 creatures with their own skeleton, ragdoll and behaviour graph: GrilledTurkey (TheFriedturkey and HcGxGrill). Their seven custom creatures from 2020–2022 (mantis, gecko, Securitron, cazador, bighorner, centaur and Project Zeta's abomination) were all made with **3ds Max 2013, Bethesda's official Havok exporter and the Creation Kit**, after "a year of research" ([Mojave Mantises](https://www.nexusmods.com/fallout4/mods/48442); [Mojave Cazadores](https://www.nexusmods.com/fallout4/mods/57161)). No open-source tool has been reported to produce a working custom FO4 ragdoll, and none writes FO4 ragdoll physics (hknp) or skeleton mappers into a `skeleton.hkx`. The most capable open codebase, G-A-R-D-E-N's MIT-licensed Behaviour Graph Studio (BGS), lists both as open issues ([BGS issues](https://github.com/G-A-R-D-E-N/BGS/issues)). Behaviour graphs are a different story. BGS edits all five FO4 Havok file types in place, byte for byte, and hkxpack has converted them to and from XML for years. Every documented route to a new creature still starts by cloning a donor creature's project and graph. For a team that already writes NIFs, animation clips and skeleton-only hkx files from Python, this leaves two jobs. The first is the ragdoll and mappers, which the team must either build (an hknp writer, starting from its own Skyrim ragdoll generator) or inherit from a vanilla skeleton. The second is root motion, which the team currently writes as zeros and which FO4's locomotion, turning and AnimTextData depend on.

## BGS edits behaviour graphs but stops at physics

**Behaviour Graph Studio** (GitHub G-A-R-D-E-N/BGS, also Nexus 107691 by NomadsReach) is C#/.NET 8 and MIT-licensed. It has its own packfile reader and writer and needs no Havok SDK. It reads FO4 behaviour, character, project, skeleton and animation hkx, including straight from `.ba2` archives ([README](https://github.com/G-A-R-D-E-N/BGS/blob/main/README.md)). The repository was created in August 2026 and is at version 1.3.0, labelled beta, last pushed 2026-10-22. Value edits are written in place with "every other byte of the file … left exactly as it shipped". Structural edits rebuild the file, and the author reports **15,320 vanilla animation files rebuilt byte for byte** and all **531 vanilla behaviour graphs** resolved. The author adds the honest caveat that this is "proven against the files themselves, which is not the same as the game accepting the result" ([Nexus 107691](https://www.nexusmods.com/fallout4/mods/107691)). Its most reusable asset is `HavokClassTypes.json`. It targets `hk_2014.1.0-r1`, takes member descriptions from hkxpack's MIT metadata, and takes instance sizes "read out of Fallout 4 itself" ([HavokClassTypes.json](https://github.com/G-A-R-D-E-N/BGS/blob/main/src/Hkx/HavokClassTypes.json); [THIRD_PARTY_NOTICES](https://github.com/G-A-R-D-E-N/BGS/blob/main/THIRD_PARTY_NOTICES.md)).

The limits matter more than the features. BGS can add, remove and reorder bones only in a *standalone* skeleton; "dependent rigs refuse edits that need animation, mapper or physics index remapping" ([RELEASE-NOTES](https://github.com/G-A-R-D-E-N/BGS/blob/main/RELEASE-NOTES.md)). Its ragdoll support is a "read-only engineering preview" that writes no hkx physics data ([ragdoll-preview doc](https://github.com/G-A-R-D-E-N/BGS/blob/main/docs/ragdoll-preview-engineering.md)). Its mapper author computes the simple mapping rows correctly (worst error about 4e-5 against vanilla), but it needs the caller to supply bone pairs, cannot create chain mappings, and "writing the rows back into a packfile is not implemented" ([skeleton-mapping-authoring.md](https://github.com/G-A-R-D-E-N/BGS/blob/main/docs/skeleton-mapping-authoring.md)). Open issues #60 (write hknp ragdoll), #61 (write mapper), #63/#65 (import animation and export it as hkx) and #52 ("collect community custom skeleton and HCT export fixtures") show that the author has no open-tool custom rigs to test against ([BGS issues](https://github.com/G-A-R-D-E-N/BGS/issues)). There is no documented library API. Automation means calling the `symrm` developer CLI (about 60 commands, including `nullsave`, `classcheck`, `hash` for AnimTextData ids, and `run` for behaviour simulation), the headless `--scan-*` modes, or an MCP server ([symrm.md](https://github.com/G-A-R-D-E-N/BGS/blob/main/guide/cli/symrm.md)). The researchers found no public report of BGS being used to author a new creature graph that worked in game.

The rest of the open toolchain is narrower:

| Tool | Licence | FO4 hk_2014 coverage | Status |
|---|---|---|---|
| hkxpack (Dexesttp) | MIT | HKX↔TagXML for behaviours, skeletons and more; class XML must be pulled from the game; some cloth data is lost | Dormant since 2020 ([GitHub](https://github.com/Dexesttp/hkxpack)) |
| HKXPack Plus (Alfred-DMB) | MIT | hkxpack fork bundling 908 class definitions, `verify`, PS4 layout | New, 2026 ([GitHub](https://github.com/Alfred-DMB/HkxPack-Plus)) |
| PyNifly | GPL-3.0 | Pure-Python FO4 spline animation and skeleton-only hkx writer; hknp collision inside NIFs | Very active ([anim_fo4.py](https://github.com/BadDogSkyrim/PyNifly/blob/main/io_scene_nifly/hkx/anim_fo4.py)) |
| havok-ps4-pipeline | MIT | Python packfile reader/writer, behaviour files only | Small reference ([GitHub](https://github.com/DevNvll/havok-ps4-pipeline)) |
| hkxcmd, ck-cmd, HKX2/hkxconv, Pandora, Nemesis | various | Skyrim hk_2010 only; no FO4 support found | Precedent only ([ck-cmd](https://github.com/aerisarn/ck-cmd)) |
| HCT 2014 + Havok Animation Tool | proprietary | Full authoring, including ragdolls | Not redistributable; users must "search … on your own" ([Nexus 56676](https://www.nexusmods.com/fallout4/mods/56676)) |

PyNifly's own format doc says its skeleton writer leaves out `localFrames` and `partitions` and covers no ragdoll, mapper or hknp content ([hkx_skeleton_format_fo4.md](https://github.com/BadDogSkyrim/PyNifly/blob/main/docs/hkx_skeleton_format_fo4.md)). That is the same ceiling as this repo's writer. Licensing shapes reuse. BGS and hkxpack logic can be ported into a permissive converter with attribution. Copying PyNifly code would make the converter GPL-3.0, although its docs remain a usable format reference. The class XML bundled in HKXPack Plus is data taken from the game, which hkxpack's author deliberately left out "to prevent possible legal issues" ([hkxpack README](https://github.com/Dexesttp/hkxpack)).

## One team built seven custom creatures, everyone else borrowed rigs

GrilledTurkey made scratch remakes, not ripped FNV meshes. Their credits list ZBrush, TopoGun and Substance Painter and repeat "faithfully recreated". Where FO4 already had a matching creature, they rigged new meshes to the **vanilla FO4 rig**. Capital Wasteland Radscorpions and Yao Guai credit only "Models, Textures and Rigging" ([CW Radscorpions](https://www.nexusmods.com/fallout4/mods/58729); [CW Yao Guai](https://www.nexusmods.com/fallout4/mods/58290)), and the brahmin, molerat, behemoth, super mutant and feral replacers follow the same pattern. Where FO4 had no counterpart, they built everything. On Mojave Geckos, TheFriedturkey is credited with "3D Models, Textures, Rigging, Animations and Skeleton" and HcG x Grill with "Scripting, Implementing, Behaviours, Skeleton, Havok Ragdoll" ([Mojave Geckos](https://www.nexusmods.com/fallout4/mods/50275)). Once the pipeline existed, the mantis took "a span of a week" ([Mojave Mantises](https://www.nexusmods.com/fallout4/mods/48442)). The centaur's spit attack runs "without any use of scripts (basically fully native creature implemented using only official tools)" ([CW Centaurs](https://www.nexusmods.com/fallout4/mods/59379)). Its 2019 predecessor, by contrast, had a spit that "was a pain to get working" ([Institute Centaurs](https://www.nexusmods.com/fallout4/mods/41476)). Even their Securitron, built around Automatron's Create-A-Bot system, has a custom skeleton that does not mix cleanly with vanilla robot parts "due some animations and arm positioning" ([CW Robot Pack](https://www.nexusmods.com/fallout4/mods/52147)). The F4NV team said in about 2021–22 that new creature animation had been close to impossible until IceStormNG's work. That work is the "New Creature Behavior and Implementation Tutorial" (Nexus 56676, December 2021), which requires the Havok Animation Tool and HCT ([Nexus 56676](https://www.nexusmods.com/fallout4/mods/56676)). Its contents could not be read, so its exact method is unknown.

Every other FNV/FO3 port borrows the closest vanilla rig, and the failures show where that approach breaks. Shadowliger's nightstalker and coyote meshes sit on Dogmeat's rig and are "a VISUAL. CHANGE. ONLY", with "oddities in the mesh in certain poses" ([Nightstalker Dogmeat Replacer](https://www.nexusmods.com/fallout4/mods/28752)). Rex's ear motion had to be cut "to avoid weird stretching" ([Cyberdog Rex](https://www.nexusmods.com/fallout4/mods/41635)). Giant ants built on the Nuka-World ant break when scaled up: the bodies "flicker and do not act like normal ragdolls, they float above the ground and spaz about" ([Giant Ants of the Commonwealth](https://www.nexusmods.com/fallout4/mods/34860)). A rigged ant queen "can't be targeted in vats with guns" and "too large causes issues" ([Ant Queen Modder's Resource](https://www.nexusmods.com/fallout4/mods/54958)). Floaters are reskinned bloatflies, and the Lamprey Floaters used "custom animation edits of the bloatfly" ([Lamprey Floaters](https://www.nexusmods.com/fallout4/mods/41180)). Name searches found no FO4 port at all of the lakelurk, giant rat, trog, tunneler or fire ant. Fallout: London, Miami and Cascadia show many new creatures, but none has published anything on how they were rigged ([FOLON creatures](https://fallout.wiki/wiki/Mod:Fallout_London/Creatures)).

GrilledTurkey's assets cannot be reused. The team has retired. Its About Me page allows patches and substantially edited files that *require* the original ([profile](https://www.nexusmods.com/profile/GrilledTurkey/about-me)). Each creature page, however, says conversion to other games is "not allowed … under any circumstances" and asset use needs permission or is barred outright ([Mojave Cazadores](https://www.nexusmods.com/fallout4/mods/57161)). A converter can at most point at a copy the user installed. Collections such as "Fallout New Vegas in Fallout 4" already distribute these mods as dependencies ([collection fgx1sr](https://www.nexusmods.com/games/fallout4/collections/fgx1sr)).

## The engine fails silently on mappers, subgraphs and AnimTextData

An FO4 creature is a chain of files: a project hkx points to a character hkx (whose `rigname` names the skeleton), which points to a root behaviour ([FO4 Havok Guide](https://forums.nexusmods.com/topic/9329348-fallout-4-havok-guide/)). The race then attaches further behaviours as **subgraphs** chosen by role (MT, Weapon, Furniture) and keyword. The CK documentation has a hard rule here: "only behavior graphs shipped as subgraphs to the race's root project are supported". Template races must share the template's skeleton and behaviour graph ([Subgraphs](https://fallout.wiki/wiki/Resource:Creation_Kit/Subgraphs)). After that, the CK must generate **AnimTextData** with `CreationKit.exe -GenerateAnimInfo:<ESM> … --speed [--stance]`. This writes speed translation, offsets, stance, sync and clip-generator data into folders of files with 19-digit names. If any clip the graph needs is missing, no data is generated. Modders report slow-motion playback cured by regenerating with different flags, and a batch workflow that breaks on the next-gen CK ([Subgraphs](https://fallout.wiki/wiki/Resource:Creation_Kit/Subgraphs); [Nexus 41209](https://www.nexusmods.com/fallout4/mods/41209); [Nexus article 548](https://www.nexusmods.com/fallout4/articles/548)). The researchers found no documentation of how the 19-digit names are derived. BGS's `symrm hash` computes subgraph ids, which makes it the best lead ([symrm.md](https://github.com/G-A-R-D-E-N/BGS/blob/main/guide/cli/symrm.md)).

The skeleton side fails silently. A vanilla `skeleton.hkx` holds the animation skeleton, a separate ragdoll skeleton with hknp physics, and two mappers. Each mapper row is a **model-space** transform that pairs bones with different names (`LArm_UpperArm` ↔ `Ragdoll_NPC L UpperArm`), so the pairings cannot be rebuilt by matching names. The two directions are not mirror images. Shipped mappers also contain chain mappings whose meaning is not yet understood. Above all, "Fallout 4 performs no validation at load time": a malformed mapper is never reported in game ([BGS mapper doc](https://raw.githubusercontent.com/G-A-R-D-E-N/BGS/main/docs/skeleton-mapping-authoring.md)). A third-party engine finds that FO4 skeleton NIFs carry no per-bone physics bodies, so all ragdoll physics lives in the hkx ([ByroRedux #6070](https://github.com/matiaszanolli/ByroRedux/issues/6070)). Modders also report that a custom player-race skeleton crashes unless it sits in `CharacterAssets` ([Nexus 26135](https://www.nexusmods.com/fallout4/mods/26135)), and that renamed or new graphs are "not recognized" by the CK ([Nexus forums](https://forums.nexusmods.com/topic/3367530-animations-in-skyrim)). The hknp class layout inside a creature skeleton.hkx (`hknpRagdollData`, constraint types, collision layers) has no readable public description. Even BGS's ragdoll doc deliberately leaves it out.

Root motion is the other contract this team currently breaks. FO4 locomotion, killmove and some furniture clips carry uncompressed motion in `hkaDefaultAnimatedReferenceFrame`, extracted from the Root bone ([PyNifly #381](https://github.com/BadDogSkyrim/PyNifly/issues/381)). Turn clips store their rotation as reference-frame yaw (0 → −1.5708 rad, near-zero translation), so a converter that drops it produces turn clips that do not turn. Malformed reference-frame data silently drops root motion ([ByroRedux #6241](https://github.com/matiaszanolli/ByroRedux/issues/6241); [#5894](https://github.com/matiaszanolli/ByroRedux/issues/5894)). This is unlike Skyrim, where the engine drives most movement from movement-type speeds ([Beyond Skyrim AU](https://wiki.beyondskyrim.org/wiki/Arcane_University:Implementation_of_Custom_Animations)). On FO4, zeroed extracted motion plus AnimTextData `--speed` means AnimationSpeedInfo is computed from clips that do not move. The expected results are moonwalking, sliding and broken turns, although nobody has published a measurement of this exact case. Additive clips subtract frame 0, and paired clips hold a 4×4 offset in `hkSimpleLocalFrame` ([PyNifly #381](https://github.com/BadDogSkyrim/PyNifly/issues/381)). One reported census finds a large share of vanilla clips (856) are `hkaLosslessCompressedAnimation` paired with reference frames ([ByroRedux #5897](https://github.com/matiaszanolli/ByroRedux/issues/5897)). BGS separately cites 856 *spline*-compressed files in its rebuild test, so the compression split should be re-measured locally before anything is built on it. On the record side, attack data is keyed by the graph's attack event names and applies only to combat events ([Actor](https://falloutck.uesp.net/wiki/Actor)). BodyPartData part nodes must name skeleton bones, and a mismatch there gives the typical "only decapitation works, floating vertex" symptom ([Nexus 53407](https://nexusmods.com/fallout4/mods/53407)).

## What this means for the FNV/FO3 converter

The prior art supports a **two-tier strategy**. The large majority of FNV/FO3 creatures have an FO4 body-plan match: deathclaw, radscorpion, yao guai, mole rat, brahmin, dog, bloatfly, ant, robots, super mutants and ghouls. For these, the proven route is the one GrilledTurkey used for their classic-look creatures: skin the converted mesh to the vanilla FO4 skeleton and keep its bone names and order, so the vanilla ragdoll, mappers, project, subgraphs and AnimTextData stay valid. The repo's clip retargeting and measured attack, movement and combat-style rules plug into this tier directly. The documented limits of the tier are proportions (scaling breaks ragdolls and VATS, as the ant mods show) and extra appendages (no new bones). The Skyrim precedent of proxy nodes in the NIF only, which the Beyond Skyrim wiki uses to change proportions without touching hkx, also forbids new bones ([Editing Animation Skeletons](https://wiki.beyondskyrim.org/wiki/Arcane_University:Editing_Animation_Skeletons)). Under the user's "accept drift" policy, this tier should cover most creatures without any physics writer.

The second tier covers creatures with no FO4 analogue: gecko, mantis, cazador, nightstalker, lakelurk, centaur, trog, tunneler, spore carrier and Securitron. These need what no open tool has done, which is an FO4 **hknp ragdoll and both skeleton mappers** written into skeleton.hkx. This repo is unusually well placed for it. It already has a Skyrim (hk_2010) creature skeleton, ragdoll and behaviour generator, so the body-segment geometry, constraint limits and bone pairing logic exist. What changes is the serialisation target (hknp in packfile v11) and the mapper math, which BGS has already checked against vanilla (model-space `inverse(A)·B`, unit scale within 1e-3). The pairings themselves must come from the generator, because name matching cannot produce them. The safest path is to clone a vanilla FO4 creature skeleton.hkx and diff against it, using BGS `nullsave`/`classcheck` and hkxpack XML as oracles. Since the engine performs no mapper validation, an in-game death test for each creature is the only real acceptance check. For behaviour, every source agrees on cloning a donor FO4 project and graph, renaming clips and registering subgraphs under that project, and not generating graphs from scratch. The Skyrim graph generator's value is in knowing which states and events a creature needs, not in emitting FO4 graphs directly.

Root motion is the cheapest high-value fix and applies to both tiers. Writing real `hkaDefaultAnimatedReferenceFrame` data (translation and yaw extracted from the FNV/FO3 accumulation root, `Bip01 NonAccum`) is a contained change to the existing animation writer. Without it, measured movement speeds cannot match AnimTextData. The other unknowns are researchable from vanilla data the team can read: the creature variable and event set (dump a vanilla quadruped project with BGS or hkxpack), the hknp ragdoll layout (inspect a vanilla creature skeleton.hkx), and the AnimTextData naming hash. One more unknown is whether `-GenerateAnimInfo` can be run headless as part of the build. Its documented failure modes argue for checking that its output exists for every clip.

## Conclusion

The bottleneck has moved. In 2021 it was behaviour authoring, which only the proprietary Havok Animation Tool could do. In 2026 open tools can read, edit and rebuild FO4 graphs, and the gap that remains is physics serialisation: ragdolls and mappers, a format no open project has written and the engine never validates. That gap fits this converter's strengths. A team that already generates Skyrim ragdolls and FO4 skeletons could become the first open producer of FO4 creature ragdolls. The work that would make that possible is narrow: the hknp layout, the mapper math BGS has already checked, and a vanilla clone to diff against.

The evidence also argues against perfectionism. GrilledTurkey's own classic-look creatures sit on vanilla rigs, and the community's practice shows that most FNV/FO3 creatures need only a mesh, retargeted clips with real root motion, and a donor project. Custom rigs are worth their cost only for the roughly ten creatures FO4 has no body plan for. Until an open ragdoll writer exists, the only working examples of those in FO4 remain GrilledTurkey's mods, which users install themselves and which cannot legally be converted or redistributed.
